# Supported behavior and delivery gates

This document records implementation progress and known limitations.

This is the working-tree implementation status. Browser acceptance recorded 64 passing behavior/CSP/SRI pairs at `d6c6b42`, followed by synthetic CAPTCHA completion and denial checks after isolated challenge origins and bounded dynamic provider routing were added.

## Supported workflow

Generated prose, functional values and diagnostic preservation are delivery requirements. Verifying the serving revision when investigating a browser report is part of correctness.

The behavior-preservation checkpoint covers image, JavaScript-navigation and malformed-source changes. The expanded 15-pair Chrome comparison passed at `d6c6b42`, including the corrected decoded-CSP-hash case.

Blinder supports a configured target reached through a local HTTPS reverse proxy, directly or through Tor SOCKS5. Synthetic acceptance covers login/logout and cookies, browser-origin form submissions, JSON, gzip, upstream TLS verification, fragmented WebSocket text, certificate persistence and evidence output. See the repeatable checks and separately recorded browser results in [testing](testing.md).

Origin and Referer translation uses recognized local origins, including scheme and port, for HTTP and WebSocket. Unrelated, opaque, malformed and duplicate origins remain unchanged. Multi-origin routing is supported: `--extra-origin` (repeatable) registers additional upstream origins, each served under a deterministic alias hostname (`host-<sha256[:4]>.<alias>`). The proxy routes by Host header, the TLS certificate covers all alias SANs, and CORS Access-Control-Allow-Origin headers map each upstream origin to its local alias. Same-upstream Location and Content-Location headers retain the browser's validated entry origin, including when served from caches; extra origins retain separate aliases.

Registered resource URLs in HTML attributes, CSS URLs/imports and complete unescaped JavaScript URL literals use that same validated browser entry hostname and port. For example, opening the primary target through `https://127.0.0.1:8099` keeps its absolute resource URLs on that origin; resources from a registered extra origin still use their distinct alias. Response and SRI caches partition transformed bytes by entry authority, and SRI prefetch selects the authority of the eventual resource request. This avoids replaying bytes or integrity values generated for another entry hostname. Dynamically assembled or escaped URLs still need workflow-specific checks.

Complete registered local URLs submitted as JSON, form/query values or reassembled WebSocket text regain their upstream scheme, hostname and port before ordinary alias restoration. JSON restoration edits changed strings while retaining number precision, unchanged spelling and scoped opaque CAPTCHA values. This handles complete URL values; it does not guess at URLs embedded in arbitrary prose or malformed payloads.

The CLI reserves the listen port before certificate/trust work, reports readiness only after setup, exits on listener failure, and returns nonzero if shutdown or a requested artifact write fails. Certificate-only setup does not bind a port. Both artifact destinations are attempted even if one fails. The published d659e9c checkpoint passed the functional CI step. Subsequent external CSP/SRI verification was run locally.

## Resource and protocol controls

| Area | Implemented behavior |
| --- | --- |
| Requests | Buffered; 50 MiB maximum including unknown-length bodies. Read failures return 400; oversized bodies return 413 before forwarding. |
| Responses | Identity/gzip decoding; 50 MiB after decompression. Unsupported encodings and read/size failures return a generic 502. No large-response streaming fallback. |
| Timeouts | Default 30-second upstream deadline includes response reading; client timeout defaults to 60 seconds. |
| JSON | Valid documents keep whitespace, order, duplicate members, numeric spellings and unchanged string escapes. Only changed string tokens are re-encoded. Malformed responses retain diagnostic text and broken grammar when string escapes are unambiguous; ambiguous escapes or scrub-induced key collisions produce `null`. |
| URL paths | Issued mappings are restored per escaped segment before submission scoping, version checks and cache lookup. Unchanged escapes are retained; restored slash/question/hash characters remain path data. HTTP and WebSocket share this restoration. |
| Forms and queries | Restore only changed decoded components; retain pair order, duplicate parameters, bare keys, empty segments and untouched percent-escape/space spellings. Malformed percent encoding reaches upstream unchanged. Scoped CAPTCHA values remain opaque. |
| Response headers | Custom end-to-end diagnostic fields survive configured value redaction. Identity-bearing custom field names remain suppressed. Hop-by-hop fields, Connection-nominated fields and invalidated framing/digest/range metadata are removed. |
| Identity matching | Unicode-aware configured matching without rescanning replacements; configured-token findings use a generic label. |
| WebSocket | Handshake, masking, fragmentation, frame lengths and UTF-8 validated. Text is scrubbed after reassembly. Frames/reassembled text limited to 16 MiB. Extensions are not negotiated. |
| Connection lifecycle | WebSocket activity in either direction refreshes the idle deadline. Close handshakes wait for both peers, bounded by five seconds or the shorter idle timeout. Shutdown closes tracked connections and cancels pending dials. |
| Local TLS | Persistent 90-day leaf certificates; startup renewal with seven days or less remaining. OS-aware guidance and separate platform trust results for the listen host, primary/extra aliases, configured operator/challenge hostnames and Tor-routed CAPTCHA provider aliases. CAPTCHA certificate planning includes the challenge wildcard and checks a concrete example hostname. Provider configuration loads before certificate preparation. Preflight exit status and explicit macOS user trust apply to the listen host; selected browser trust and name resolution are checked separately. Ephemeral mode available. |
| Raster images | Bounded JPEG, static PNG and GIF inputs are fully decoded before masking. Neutral pixels replace the original pixels and metadata while retaining format and dimensions; GIF frame geometry, delay, disposal and loop count are retained. JPEG EXIF retains only orientation. Invalid binary stays undecodable, while printable error bodies retain scrubbed diagnostics. |
| Other binary replacement | Non-image binary media/documents/fonts retain the existing GIF-placeholder behavior labelled `image/gif`, with available metadata extracted separately. This deliberately loses original rendering/functionality. |

Resource controls are operational protections. Increasing a limit or adding streaming requires tests for memory, cancellation and scrubbing across chunk boundaries; removing a cap alone does not improve coverage safely.

For replicated browser controls, the acceptance criterion is the same allow, block and report decision as the original under corresponding origins. CSP inline script/style hashes now follow the original-to-rewritten source relationship: an originally invalid hash cannot become a grant just because its value matches rewritten bytes. Hash processing uses browser-normalized text, and distinct original sources remain distinguishable when rewriting would otherwise make them identical. HTML nonce attributes and policy nonces use a shared mapping. Header and meta policies retain their independent scopes, multiple enforcing policies remain intersected, and report-only policies stay report-only. CAPTCHA configuration no longer adds permissions to the target's CSP. Native Chrome passed the paired synthetic comparison; specific coverage and remaining control-fidelity work are tracked in the delivery gates below.

`javascript:` navigation attributes now use the JavaScript rewriter after URL preprocessing and percent decoding. Member expressions and executable syntax are retained while configured identities in strings use the ordinary JavaScript rules. CSP hash translation binds the original decoded URL, including its scheme, to its rewritten counterpart; a hash of the percent-encoded spelling must not become a new grant. The expanded Chrome comparison passed this correction at `d6c6b42`. This remains a limited JavaScript rewriter, not a complete parser or containment mechanism.

Image `src` references now use ordinary resource routing, retaining the real request and its upstream status rather than replacing the attribute with a valid data GIF. Embedded raster data URLs use the same decoder and masking. Raster decoding is capped at 16,384 pixels per dimension, 16,777,216 total pixels and 256 GIF frames, with cumulative GIF frame pixels counted before allocation. Legal PNG chunks, JPEG comments and GIF comments fill available size gaps; tiny gaps or an encoding larger than the source retain an observable size difference. Animated PNG/APNG, WebP, AVIF, BMP and other unsupported binary image formats do not have rendering fidelity and can become undecodable. Embedded SVG is also unsupported and masked to invalid image data; network SVG retains the separate existing XML path. PNG EXIF orientation is not preserved, and browser decoder leniency may differ from the Go decoders. These changes do not establish general image or media fidelity.

## Diagnostic and size fidelity

Proxied HTTP responses identify the view with `X-Blinder-View: transformed`. `X-Blinder-Original-Body-Bytes` and `X-Blinder-Rewritten-Body-Bytes` describe the original decoded representation and the rewritten representation respectively; `-1` means unavailable. `X-Blinder-Body-Size-Match` is `exact`, `different`, or `unknown`, based on those representation sizes. It is a length comparison, not a statement that content or application behaviour is identical. `Content-Length`, when supplied, describes the representation actually served.

`--paranoid` controls content masking and works with either direct routing or `--tor`; it does not select a network transport. In `--paranoid` mode, ordinary HTML prose uses source-dependent verse/lorem filler instead of removal messages. A private session key makes identical text stable within that session, while changed text selects a different word stream even at the same length. Each replaced text token initially keeps its source byte budget and literal boundary whitespace; whole words are followed by spaces to fill a short remainder. The corpus includes a passage from Rumi's *The Mesnevi*, Book I, XII, in [James W. Redhouse's 1881 translation](https://www.gutenberg.org/files/61724/61724-h/61724-h.htm), plus traditional lorem ipsum. Ordinary document titles use source-dependent filler within their own original byte budget, including when no other prose is available; title bytes are not used to absorb unrelated edits. Titles on HTTP 4xx/5xx responses retain their scrubbed diagnostics. Whitespace-only tokens, textarea values and option text are excluded from filler. The disclosure header still identifies the response as transformed.

Generated long prose is checked against configured identities, including complete multiword matches. Conflicting vocabulary is filtered and bounded, source-dependent alternatives are checked; unaffected output remains unchanged. If the prose vocabulary is unavailable, bounded alphanumeric alternatives retain the byte budget. Exhausting all candidates falls back to spaces and can lose a visible change; pathological exclusions and text concatenated across separate HTML nodes remain limitations. Original content tags and delta comparisons remain necessary. No blanket removal-word filter is applied to upstream diagnostics or application values.

Display spans with budgets of 1–8 bytes reserve distinct HTML-safe output within the session, including after prose resizing. Reservations retain only private tags, are never reassigned, and are capped at 4,096 with at most 8,192 candidate probes per allocation. Collision assignments depend on arrival order. A one-byte span has at most 64 available outputs, fewer when configured identities exclude candidates. Exhaustion returns a same-size fallback that can lose a content change; `short_text_fallbacks` records these attempts. Longer prose generation is unchanged and has no collision-free guarantee. The separate original-body tag remains the full-content equality signal. Size and change-signal verification is covered by the unit and functional test suites.

Functional identity values use reversible opaque aliases such as `[v:…]`, without removal labels. Configured identity matches of at least five UTF-8 bytes receive aliases of the same byte length while their fixed-width namespace has room. Payloads are derived from the private session key; exact source spelling and Unicode case variants restore independently. Shorter matches and exhausted namespaces expand. Literal-marker escaping, JSON/HTML escape spelling, domain aliases and routing edits can also change the enclosing response length; compact identity aliases do not establish whole-body matching by themselves.

After all HTML attribute, URL and SRI changes, Blinder aims to match the **whole original decoded body length** by resizing only the generated prose spans. It expands the largest prose span or shrinks prose proportionally while retaining boundary whitespace and a minimum one-byte budget per span. It does not append padding elements or cut source markup, scripts, diagnostics or submitted values. If there is insufficient generated prose, it makes the closest available match and reports the remaining difference. Without generated prose, including on error responses and in ordinary non-paranoid mode, this adjustment is not applied.

Every response targets its own upstream body length. When two responses both match, their signed length difference is retained for differential checks; no fixed page size or baseline length is imposed. For responses marked `different`, original-byte measurements remain available for length comparisons, alongside the actual rewritten size. Supported raster images use the format-specific padding described above; JSON, plain text, other binary content and compressed transfer sizes are not padded to match. Equal decoded lengths do not imply equal gzip sizes or preserve timing behaviour through buffering and caching.

HTML responses with status 400 or higher retain their diagnostic text, including the document title, under the existing configured redaction, including in paranoid mode. On HTTP 200 pages, text within `pre`, `code`, `role="alert"`, and `aria-live="assertive"` regions is also retained under that redaction. JSON error fields and number precision remain available regardless of HTTP status. Unmarked errors inside ordinary HTTP 200 HTML are not automatically recognisable; paranoid replacement can still affect them. These rules preserve useful diagnostics, not verbatim messages or a universal absence of identifying content.

Valid JSON requests and responses use source edits instead of rebuilding objects. If no string changes, the body is byte-for-byte unchanged. Existing duplicate members remain in their original order, including equivalent escaped key spellings; a transformation that makes distinct keys collide is rejected (400 for requests, `null` for responses). Request restoration also preserves configured CAPTCHA opaque values as complete raw subtrees. Changed strings may differ in length and escape spelling. Malformed responses, including concatenated documents or a missing final quote/brace, retain diagnostic text and malformed grammar after decoded string redaction. Unknown/incomplete escapes, backslashes outside strings or a residual configured identity across fragment boundaries still produce `null`; raw operator evidence retains the original. No repair into valid JSON is attempted.

Untouched HTML retains source spelling: tag case, attribute order/quoting, entities, line endings, comments and incomplete trailing markup. Existing quoted attribute values are edited in place when attribute names/order remain intact and parsing is unambiguous; tag case, boolean attributes and untouched entity/quote spellings survive. Other changed attributes use the existing serializer. Identity edits in ordinary, bogus and unterminated comments and incomplete trailing source now preserve the original envelope where the result remains unambiguous; no closing delimiter or repaired tag is invented. Identities crossing syntactic delimiters can still require omission, and raw operator evidence remains necessary. Preserving every application-security finding still requires comparison with the original response: unsupported media, changed-markup serialization and configured redaction can affect findings.

Each HTTP manifest request now has `response` measurements:

Ordinary target HTTP requests also have a session-scoped `request_id`, returned as `X-Blinder-Request-ID`, their method, and private `context_tag`/`request_tag` equality signals. The offline [response comparison tool](response-deltas.md) accepts explicit baseline/test IDs from one session, reports per-response size fidelity and content/status changes, and keeps baseline variation visible. It excludes cached, incomplete and otherwise unavailable bodies from fresh-upstream comparisons. Provider/operator requests and WebSocket messages are outside this first comparator.

| Field | Meaning |
| --- | --- |
| `source` | `upstream`, `cache`, `sri-cache`, or a proxy-generated response |
| `upstream[]` | Main-resource attempts, including CAPTCHA retries: actual upstream status, encoded payload bytes read, decoded bytes read, completion and a generic failure category. HTTP framing/TLS overhead is excluded. Status 0 means no upstream response. SRI prefetches and provider-relay requests are separate transactions. |
| `original_body_tag` | Session-keyed HMAC of the complete decoded original body, also exposed as `X-Blinder-Original-Body-Tag`. Retained across response/SRI cache hits and associated conditional responses. Absent for unavailable originals, uncached HEAD/304 and proxy errors. It is an equality signal, not a public fingerprint or an exploit verdict; it changes across proxy sessions. |
| `rewritten_body_tag` / `body_complete` | SHA-256 of the full rewritten body accepted by the HTTP writer, only when the original is known and the complete ordinary representation was written without error. Missing/false for HEAD, bodyless statuses, local failures and partial writes. These fields do not prove receipt by the client. |
| `original_body_bytes` / `rewritten_body_bytes` | Representation sizes, retained across response/SRI cache hits when measured. Unknown values are -1. |
| `downstream_body_bytes` | Body bytes accepted by the HTTP writer; zero for HEAD/304. This is not proof of client delivery. |
| `rewrite_delta_bytes` | Rewritten minus original representation bytes, or null when either size is unavailable. |
| `short_text_fallbacks` | Request-local count of short display-text generation attempts that could not reserve a unique output. Includes intermediate prose resizing; not a count of responses or proven collisions. Cache hits make no new generation attempts. Zero does not establish collision-free longer prose. |

A partial read reports observed counts with `complete: false`, not an invented full length. A cache hit has no new upstream attempt. Revalidation can therefore record a zero-byte upstream 304 alongside a cached representation and a nonempty downstream body. An uncached HEAD cannot establish the rewritten representation length or ETag; those headers are omitted. Transports that already decompressed a body report its encoded size as unknown.

## Evidence

HAR retains pre-scrub upstream HTTP data. Its configured per-body cap now covers request bodies and text/binary responses. Original sizes and truncation comments remain available; UTF-8 truncation avoids splitting a code point. Binary/invalid-UTF-8 request data uses the explicit `postData._encoding: "base64"` extension. Response binary data uses HAR's `content.encoding`. Request start timestamps account for elapsed upstream time.

For measured main-resource and SRI-fetch transactions, HAR `bodySize` records encoded payload bytes and `content.size` records decoded bytes. SRI prefetch errors retain bounded non-200/partial bodies as evidence without accepting them as verified resources. Failed reads preserve the upstream status, headers and available body separately from the generic error sent downstream. Transport failures use upstream status 0 and put the diagnostic in the capture comment. Original request bodies remain in failure evidence; capture truncation comments are retained.

HAR flushes automatically every 30 seconds for durability across crashes, merging new entries with any existing file on disk. A configurable memory cap (maxEntries) auto-flushes when the in-memory buffer exceeds the threshold. Export streams existing entries and journal records, and serializes append/export/removal within one writer; retryable append failures roll back their partial snapshot. A process crash between replacing the final HAR and removing its journal can still replay entries on restart. Failed upstream requests (dial errors, body read failures) and WebSocket upgrade transactions are captured with full request details and error/status information. A synthetic seven-transaction export passes independent HAR 1.2 schema validation, including required cookie arrays, cache objects and redirect URLs. The fixture also checks binary decoding, partial errors, transport failures and 101 handshakes. Import into the chosen viewer and replay remain separate acceptance checks, particularly for the request encoding extension.

Playwright 1.62.1's installed HAR importer/matcher was also tested independently. It does not decode Blinder's binary-request extension; the optional [local export adapter](playwright-har-export.md) writes lossless request attachments in that consumer's format while leaving the canonical capture unchanged. Matching verifies the original binary request and response bytes. This check launches no browser and does not establish viewer UI or browser replay acceptance.

HTTP manifest entries include success and failure status plus request-local identity/domain replacement counts, isolated across concurrent requests. `scrub_count` measures gate matches, not every structural transformation such as image/title replacement. `leak_count` measures residual target-domain and identity-token occurrences in scrubbed output; 0 means the scrubber caught every configured pattern in that response. The legacy scrub report's `total_leaks` counts recorded matches, not proof that those identities reached the client. Repeated manifest flushes replace the finding snapshot rather than multiplying counts.

WebSocket handshakes are recorded in HAR and the manifest before a successful frame relay finishes. Refused upgrades preserve the actual upstream status and scrubbed diagnostics through the bounded HTTP rewrite path; partial failures retain raw upstream evidence. Frame traffic is not counted as an HTTP body or captured as a HAR transaction. Complete metadata extraction remains open. Raw evidence, mappings and identity metadata belong only on the operator's side.

## CAPTCHA provider routing

In Tor mode, every configured `route-with-target` origin has a deterministic `captcha-<hash>.localhost` alias on the proxy listener. Scheme, hostname and effective port distinguish origins. These routes never enter the target cookie-restoration, cache or SRI scope. Exact origin validation and optional URL regexes authorize each upstream request; an alias does not grant access to an entire provider site. Paths, escapes, duplicate query values and bodies remain opaque. Direct mode leaves provider references intact, and an explicit `tor_policy: direct` keeps its browser-direct behavior.

Provider HTML maps registered static URL attributes, base URLs and refresh navigation to aliases; dispatch still enforces the resource regex. Provider CSP and report-only policies retain their directives, nonces and hashes while registered source origins translate. For documents without policy, a routing helper handles dynamic fetch, XHR, URL-property setters and `setAttribute` without editing provider script bytes or SRI metadata. It is skipped for any enforcing/report-only header or meta policy, a leading BOM, invalid UTF-8 or unsupported explicit charset. It does not cover parser-created URLs through `innerHTML`/`insertAdjacentHTML`, workers, imports, CSS or every browser API. Unknown origins remain unchanged; this helper is not network containment. Changed responses report transformation provenance and real decoded/output byte counts.

CORS preflights, including OPTIONS, reach upstream and retain its real decisions. All syntactically valid HTTP methods pass through; issued method aliases are restored before forwarding, and corresponding preflight grants are translated without creating permission. Upstream error statuses and bodies remain visible. The provider path caps request bodies at 2 MiB and responses at 10 MiB and uses the configured upstream timeout. Browser APIs retain their own method restrictions.

Browser cookies are scoped to the provider aliases, shared across challenges as the browser normally manages them. Exact upstream-host Domain attributes become host-only; broader domain-cookie sharing is not reproduced. Reserved operator credentials are excluded. This replaces the old relay's per-challenge cookie jars for browser provider traffic; reproducing upstream SameSite and sibling-domain relationships remains open.

Operator controls stay on `https://blinder-operator.localhost:<listen-port>/__blinder/captcha/`, require a loopback peer and authentication, and use a Secure, HttpOnly, host-only `__Host-` cookie. Cookie-authenticated mutations require the configured operator Origin. Raw challenge documents use separate `<id>.blinder-challenge.localhost` origins with expiring, challenge-bound view capabilities; operator credentials do not authorize those views. Their bridge checks the configured operator origin and is omitted when policies, BOM or charset prevent safe instrumentation. Target and operator origins still return 404 for the old `/__blinder/captcha/res` endpoint. Certificate planning includes `*.blinder-challenge.localhost`; that does not establish browser trust.

The current synthetic operator flow passed in Chrome: the direct positive baseline and proxy each exercised 13 provider requests, all proxy requests matched relay observations, and operator submission resumed the original POST with its exact token, session and refreshed CSRF. The separate cross-site Lax-cookie profile produced the same visible POST 400 directly and through the proxy, with six requests each and no proxy-generated `Origin: null` preflight. This preserves a browser denial instead of weakening cookies to force completion. The current operator isolation check also passed with an active target service worker, denied cross-origin access and an authenticated popup whose opener was severed.

Raw challenge policy fidelity is still incomplete: a CSP `'self'` source at the new challenge origin does not automatically authorize target assets served from a different local origin. Retaining the policy headers alone does not establish matching browser decisions. CSP-restricted completion, broader dynamic APIs, upstream sibling-domain cookie relationships, actual challenge/provider TLS trust and real-provider human completion remain gates. The live Tor attempt reached only 5% bootstrap in 90 seconds without a specific logged failure; it established no exit or onion acceptance.

## Remaining delivery gates

SRI version-reference ownership uses a random persistent signing key, independent of public configuration and certificate renewal. Authentic references whose in-memory records are gone fail closed; unissued application query values pass through even if they resemble a token. CLI restarts retain this key, including with ephemeral TLS. Embedded callers must supply `VersionKeyDir` or `CertDir` for ownership across server instances; an empty directory selects an in-memory registry.

These are implementation work and acceptance criteria, not waived requirements.
