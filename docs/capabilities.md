## Supported workflow

Blinder supports a configured target reached through a local HTTPS reverse proxy, directly or through Tor SOCKS5. Synthetic acceptance covers login/logout and cookies, browser-origin form submissions, JSON, gzip, upstream TLS verification, fragmented WebSocket text, certificate persistence and evidence output. See the repeatable checks and separately recorded browser results in [testing](testing.md).

Origin and Referer translation uses recognized local origins, including scheme and port, for HTTP and WebSocket. Unrelated, opaque, malformed and duplicate origins remain unchanged. Multi-origin routing is supported: `--extra-origin` (repeatable) registers additional upstream origins, each served under a deterministic alias hostname (`host-<sha256[:4]>.<alias>`). The proxy routes by Host header, the TLS certificate covers all alias SANs, and CORS Access-Control-Allow-Origin headers map each upstream origin to its local alias. Same-upstream Location and Content-Location headers retain the browser's validated entry origin, including when served from caches; extra origins retain separate aliases.

Registered resource URLs in HTML attributes, CSS URLs/imports and complete unescaped JavaScript URL literals use that same validated browser entry hostname and port. For example, opening the primary target through `https://127.0.0.1:8099` keeps its absolute resource URLs on that origin; resources from a registered extra origin still use their distinct alias. Response and SRI caches partition transformed bytes by entry authority, and SRI prefetch selects the authority of the eventual resource request. This avoids replaying bytes or integrity values generated for another entry hostname. Dynamically assembled or escaped URLs still need workflow-specific checks.

Complete registered local URLs submitted as JSON, form/query values or reassembled WebSocket text regain their upstream scheme, hostname and port before ordinary alias restoration. JSON restoration edits changed strings while retaining number precision, unchanged spelling and scoped opaque CAPTCHA values. This handles complete URL values; it does not guess at URLs embedded in arbitrary prose or malformed payloads.

The CLI reserves the listen port before certificate/trust work, reports readiness only after setup, exits on listener failure, and returns nonzero if shutdown or a requested artifact write fails. Certificate-only setup does not bind a port. Both artifact destinations are attempted even if one fails. The published d659e9c checkpoint passed the functional CI step. Subsequent external CSP/SRI verification was run locally.

## Resource and protocol controls

| Area | Implemented behavior |
| --- | --- |
| Requests | Buffered; 50 MiB maximum including unknown-length bodies. Read failures return 400; oversized bodies return 413 before forwarding. |
| Responses | Identity/gzip decoding; 50 MiB after decompression. Unsupported encodings and read/size failures return a generic 502. No large-response streaming fallback. |
| Timeouts | Default 30-second upstream deadline includes response reading; client timeout defaults to 60 seconds. |
| JSON | Valid documents keep whitespace, order, duplicate members, numeric spellings and unchanged string escapes. Only changed string tokens are re-encoded. Malformed responses retain diagnostic text and broken grammar when string escapes are unambiguous; ambiguous escapes or scrub-induced key collisions produce `null`. |
| URL paths | Issued mappings are restored per escaped segment before submission scoping, version checks and cache lookup. Unchanged escapes are retained; restored slash/question/hash characters remain path data. HTTP and WebSocket share this restoration. |
| Forms and queries | Restore only changed decoded components; retain pair order, duplicate parameters, bare keys, empty segments and untouched percent-escape/space spellings. Malformed percent encoding reaches upstream unchanged. Scoped CAPTCHA values remain opaque. |
| Response headers | Custom end-to-end diagnostic fields survive configured value redaction. Identity-bearing custom field names remain suppressed. Hop-by-hop fields, Connection-nominated fields and invalidated framing/digest/range metadata are removed. |
| Identity matching | Unicode-aware configured matching without rescanning replacements; configured-token findings use a generic label. |
| WebSocket | Handshake, masking, fragmentation, frame lengths and UTF-8 validated. Text is scrubbed after reassembly. Frames/reassembled text limited to 16 MiB. Extensions are not negotiated. |
| Connection lifecycle | WebSocket activity in either direction refreshes the idle deadline. Close handshakes wait for both peers, bounded by five seconds or the shorter idle timeout. Shutdown closes tracked connections and cancels pending dials. |
| Local TLS | Persistent 90-day leaf certificates; startup renewal with seven days or less remaining. OS-aware guidance and separate platform trust results for the listen host, primary/extra aliases and configured operator hostname. Preflight exit status and explicit macOS user trust apply to the listen host; selected browser trust and name resolution are checked separately. Ephemeral mode available. |
| Binary replacement | Supported binary media/documents/fonts become a GIF placeholder labelled `image/gif`, with available metadata extracted separately. This deliberately loses original rendering/functionality. |

Resource controls are operational protections. Increasing a limit or adding streaming requires tests for memory, cancellation and scrubbing across chunk boundaries; removing a cap alone does not improve coverage safely.

For replicated browser controls, the acceptance criterion is the same allow, block and report decision as the original under corresponding origins. CSP inline script/style hashes now follow the original-to-rewritten source relationship: an originally invalid hash cannot become a grant just because its value matches rewritten bytes. Hash processing uses browser-normalized text, and distinct original sources remain distinguishable when rewriting would otherwise make them identical. HTML nonce attributes and policy nonces use a shared mapping. Header and meta policies retain their independent scopes, multiple enforcing policies remain intersected, and report-only policies stay report-only. CAPTCHA configuration no longer adds permissions to the target's CSP. Native Chrome passed the [paired synthetic comparison](testing-results-2026-09-26-csp.md); that report records the specific coverage and remaining control-fidelity work.

## Diagnostic and size fidelity

Proxied HTTP responses identify the view with `X-Blinder-View: transformed`. `X-Blinder-Original-Body-Bytes` and `X-Blinder-Rewritten-Body-Bytes` describe the original decoded representation and the rewritten representation respectively; `-1` means unavailable. `X-Blinder-Body-Size-Match` is `exact`, `different`, or `unknown`, based on those representation sizes. It is a length comparison, not a statement that content or application behaviour is identical. `Content-Length`, when supplied, describes the representation actually served.

`--paranoid` controls content masking and works with either direct routing or `--tor`; it does not select a network transport. In `--paranoid` mode, ordinary HTML prose uses deterministic verse/lorem filler instead of removal messages. Each replaced text token initially keeps its source byte budget and literal boundary whitespace; whole words are followed by spaces to fill a short remainder. The corpus includes a passage from Rumi's *The Mesnevi*, Book I, XII, in [James W. Redhouse's 1881 translation](https://www.gutenberg.org/files/61724/61724-h/61724-h.htm), plus traditional lorem ipsum. Ordinary document titles become `Transformed view`; titles on HTTP 4xx/5xx responses retain their scrubbed diagnostics. Whitespace-only tokens, textarea values and option text are excluded from filler; functional values still use the existing reversible mappings. Functional values use reversible opaque aliases such as `[v:…]`, without removal labels. The disclosure header still identifies the response as transformed.

After all HTML attribute, URL and SRI changes, Blinder aims to match the **whole original decoded body length** by resizing only the generated prose spans. It expands the largest prose span or shrinks prose proportionally while retaining boundary whitespace and at least one visible byte per span. It does not append padding elements or cut source markup, scripts, diagnostics or submitted values. If there is insufficient generated prose, it makes the closest available match and reports the remaining difference. Without generated prose, including on error responses and in ordinary non-paranoid mode, this adjustment is not applied.

Every response targets its own upstream body length. When two responses both match, their signed length difference is retained for differential checks; no fixed page size or baseline length is imposed. For responses marked `different`, original-byte measurements remain available for length comparisons, alongside the actual rewritten size. JSON, plain text, binary content and compressed transfer sizes are not padded to match. Equal decoded HTML lengths do not imply equal gzip sizes or preserve timing behaviour through buffering and caching.

HTML responses with status 400 or higher retain their diagnostic text, including the document title, under the existing configured redaction, including in paranoid mode. On HTTP 200 pages, text within `pre`, `code`, `role="alert"`, and `aria-live="assertive"` regions is also retained under that redaction. JSON error fields and number precision remain available regardless of HTTP status. Unmarked errors inside ordinary HTTP 200 HTML are not automatically recognisable; paranoid replacement can still affect them. These rules preserve useful diagnostics, not verbatim messages or a universal absence of identifying content.

Valid JSON requests and responses use source edits instead of rebuilding objects. If no string changes, the body is byte-for-byte unchanged. Existing duplicate members remain in their original order, including equivalent escaped key spellings; a transformation that makes distinct keys collide is rejected (400 for requests, `null` for responses). Request restoration also preserves configured CAPTCHA opaque values as complete raw subtrees. Changed strings may differ in length and escape spelling. Malformed responses, including concatenated documents or a missing final quote/brace, retain diagnostic text and malformed grammar after decoded string redaction. Unknown/incomplete escapes, backslashes outside strings or a residual configured identity across fragment boundaries still produce `null`; raw operator evidence retains the original. No repair into valid JSON is attempted.

Untouched HTML retains source spelling: tag case, attribute order/quoting, entities, line endings, comments and incomplete trailing markup. Changed attributes use the existing serializer; configured identities in comments are scrubbed, while ambiguous identity-bearing incomplete markup is omitted. Preserving every application-security finding still requires comparison with the original response: image substitution, changed-markup serialization and configured redaction can affect findings.

Each HTTP manifest request now has `response` measurements:

| Field | Meaning |
| --- | --- |
| `source` | `upstream`, `cache`, `sri-cache`, or a proxy-generated response |
| `upstream[]` | Main-resource attempts, including CAPTCHA retries: actual upstream status, encoded payload bytes read, decoded bytes read, completion and a generic failure category. HTTP framing/TLS overhead is excluded. Status 0 means no upstream response. SRI prefetches and provider-relay requests are separate transactions. |
| `original_body_bytes` / `rewritten_body_bytes` | Representation sizes, retained across response/SRI cache hits when measured. Unknown values are -1. |
| `downstream_body_bytes` | Body bytes accepted by the HTTP writer; zero for HEAD/304. This is not proof of client delivery. |
| `rewrite_delta_bytes` | Rewritten minus original representation bytes, or null when either size is unavailable. |

A partial read reports observed counts with `complete: false`, not an invented full length. A cache hit has no new upstream attempt. Revalidation can therefore record a zero-byte upstream 304 alongside a cached representation and a nonempty downstream body. An uncached HEAD cannot establish the rewritten representation length or ETag; those headers are omitted. Transports that already decompressed a body report its encoded size as unknown.

## Evidence

HAR retains pre-scrub upstream HTTP data. Its configured per-body cap now covers request bodies and text/binary responses. Original sizes and truncation comments remain available; UTF-8 truncation avoids splitting a code point. Binary/invalid-UTF-8 request data uses the explicit `postData._encoding: "base64"` extension. Response binary data uses HAR's `content.encoding`. Request start timestamps account for elapsed upstream time.

For measured main-resource and SRI-fetch transactions, HAR `bodySize` records encoded payload bytes and `content.size` records decoded bytes. SRI prefetch errors retain bounded non-200/partial bodies as evidence without accepting them as verified resources. Failed reads preserve the upstream status, headers and available body separately from the generic error sent downstream. Transport failures use upstream status 0 and put the diagnostic in the capture comment. Original request bodies remain in failure evidence; capture truncation comments are retained.

HAR flushes automatically every 30 seconds for durability across crashes, merging new entries with any existing file on disk. A configurable memory cap (maxEntries) auto-flushes when the in-memory buffer exceeds the threshold. Export streams existing entries and journal records, and serializes append/export/removal within one writer; retryable append failures roll back their partial snapshot. A process crash between replacing the final HAR and removing its journal can still replay entries on restart. Failed upstream requests (dial errors, body read failures) and WebSocket upgrade transactions are captured with full request details and error/status information. A synthetic seven-transaction export passes independent HAR 1.2 schema validation, including required cookie arrays, cache objects and redirect URLs. The fixture also checks binary decoding, partial errors, transport failures and 101 handshakes. Import into the chosen viewer and replay remain separate acceptance checks, particularly for the request encoding extension.

Playwright 1.62.1's installed HAR importer/matcher was also tested independently. It does not decode Blinder's binary-request extension; the optional [local export adapter](playwright-har-export.md) writes lossless request attachments in that consumer's format while leaving the canonical capture unchanged. Matching verifies the original binary request and response bytes. This check launches no browser and does not establish viewer UI or browser replay acceptance.

HTTP manifest entries include success and failure status plus request-local identity/domain replacement counts, isolated across concurrent requests. `scrub_count` measures gate matches, not every structural transformation such as image/title replacement. `leak_count` measures residual target-domain and identity-token occurrences in scrubbed output; 0 means the scrubber caught every configured pattern in that response. The legacy scrub report's `total_leaks` counts recorded matches, not proof that those identities reached the client. Repeated manifest flushes replace the finding snapshot rather than multiplying counts.

WebSocket handshakes are recorded in HAR and the manifest before a successful frame relay finishes. Refused upgrades preserve the actual upstream status and scrubbed diagnostics through the bounded HTTP rewrite path; partial failures retain raw upstream evidence. Frame traffic is not counted as an HTTP body or captured as a HAR transaction. Complete metadata extraction remains open. Raw evidence, mappings and identity metadata belong only on the operator's side.

## Remaining delivery gates

Configured CAPTCHA resource URLs are handled before identity scrubbing, with full-origin and optional URL-regex scope. HTML-decoded paths, query values and fragments are preserved. Direct mode leaves these references intact; Tor mode relays matched `route-with-target` references through the target transport. The operator's sandboxed challenge and nested provider documents route fetch, XHR, and supported DOM URL assignments through that relay. Pending challenges have separate provider cookie jars; browser/operator credentials are not forwarded to providers. In-scope redirects retain the challenge session.

Operator controls use a separate origin, `https://blinder-operator.localhost:<listen-port>/__blinder/captcha/`, on the same listener. Access requires a loopback peer and operator authentication. The browser session uses a Secure, HttpOnly, host-only `__Host-` cookie; cookie-authenticated mutations also require the configured operator Origin. Target origins return 404 for operator controls, retaining only the scoped `/res` relay. Raw challenge/provider documents are sandboxed without the operator's origin privileges. Browser acceptance verifies authenticated popup isolation while a target service worker is active, denied cross-origin fetch/frame reads, and no operator cookie on target requests. It does not disable target service workers or alter target security policies to achieve isolation.

The resource relay accepts every syntactically valid HTTP method, including extension methods, preserving its case and body. CORS preflights authorize the requested method; ordinary OPTIONS requests reach the provider. Methods other than GET/HEAD require an active challenge session. Successful custom methods invalidate target response caches unless their semantics are known to be safe. Request bodies remain capped at 2 MiB and resource responses at 10 MiB, with the configured upstream timeout. Browser APIs still impose their own [method restrictions](https://fetch.spec.whatwg.org/#methods); accepting the CONNECT method does not implement a general-purpose TCP tunnel.

A real browser synthetic flow covers redirects, nested frames, dynamic scripts, JSON POST, credentialed XHR, PUT/PATCH/DELETE/OPTIONS, WebDAV and a custom case-sensitive method, followed by operator submission and resumption of the original target session. Successful native operator submissions receive a visible receipt; failures retain their status and retry controls. Automatic callbacks stop after initiating a submission; cookie-only fetch/XHR remains unauthorised for operator controls. The operator's Tor CSP blocks unhandled direct resource requests; `tor_policy: direct` is an explicit exception. Dynamic workers/CSS, provider origin expectations, and real human completion still need provider-specific browser acceptance. These fixtures do not establish universal CAPTCHA compatibility.

SRI version-reference ownership uses a random persistent signing key, independent of public configuration and certificate renewal. Authentic references whose in-memory records are gone fail closed; unissued application query values pass through even if they resemble a token. CLI restarts retain this key, including with ephemeral TLS. Embedded callers must supply `VersionKeyDir` or `CertDir` for ownership across server instances; an empty directory selects an in-memory registry.

These are implementation work and acceptance criteria, not waived requirements.

Complete anonymization is not an established property of the current implementation. Keep that distinction explicit when connecting a sensitive target to an untrusted consumer.
